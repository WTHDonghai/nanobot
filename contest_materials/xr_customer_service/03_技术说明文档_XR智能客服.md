### 1.2 数据流

```
产品文档/PDF/FAQ
       ↓
  [Parser] 解析为Markdown + 提取目录结构 → 写入临时VikingFS
       ↓
  [TreeBuilder] 从临时区迁移到正式存储(AGFS) + 入队SemanticQueue
       ↓
  [SemanticQueue] 异步语义处理队列（消峰填谷 + 熔断保护）
       ↓
  [SemanticProcessor] LLM批量生成 L0摘要 + L1概述
       ↓
  [VectorDB] SemanticProcessor 直接向量化入库（Dense + Sparse）
       ↓
  就绪，等待检索
```

### 1.3 各阶段详细说明

#### Parser（文档解析）

接收原始文档（PDF/Markdown/代码/音视频），完成两件事：
1. **格式转换**：PDF → Markdown（pdfplumber / MinerU API 双策略），音视频 → Whisper 文字摘要
2. **结构提取**：从书签/大纲/字体分析中提取层级目录，按章节拆分为独立文件，写入**临时VikingFS区**

此时文件内容是纯原文，**不含** L0/L1 语义摘要——那是后续异步处理的事。

#### TreeBuilder（目录树构建）

这是 Parser 和语义处理之间的**桥梁**，负责将临时区的解析结果正式接入知识库：

```
临时VikingFS中的文档目录
    │
    ├─ ① 定位文档根目录，校验目录结构
    ├─ ② 清理文件名（处理特殊字符、中文路径等）
    ├─ ③ 确定目标URI
    │     ├─ 根据scope选择基路径: viking://resources / viking://user / viking://agent
    │     ├─ 检测GitHub/GitLab代码仓 → 提取org/repo作为目录名
    │     └─ 冲突检测: 若URI已存在 → 自动追加 _1, _2 ...
    ├─ ④ 从临时区移动到AGFS正式存储
    ├─ ⑤ 创建BuildingTree对象（轻量Context，不含正文）
    └─ ⑥ 将目录入队到SemanticQueue（待异步生成L0/L1+向量化）
```

关键设计意图：
- **Parser只管解析，TreeBuilder只管落库**，职责分离
- **临时区机制**：解析中途失败不留脏数据，AGFS中只有最终结果
- **URI冲突自动处理**：允许同名文档多次上传，自动走 `_1` / `_2` 后缀

#### SemanticQueue + SemanticProcessor（异步语义处理）

- **SemanticQueue**：任务队列，带**消峰填谷**和**熔断机制**（Circuit Breaker），防止LLM调用雪崩
- **SemanticProcessor**：消费队列中的目录节点，用LLM为每个目录生成 `.abstract.md`（L0）和 `.overview.md`（L1），**完成后直接向量化写入VectorDB**

> 注意：v5.0 架构中向量化已合入 SemanticProcessor，不再有独立的 EmbeddingQueue。SemanticProcessor 生成完摘要后直接调 embedding 模型入库。

## 二、关键技术说明

### 2.1 L0/L1/L2 三级上下文结构

这是本系统的核心创新。不同于传统RAG将文档切分为等长chunk后扁平存储，我们采用**层级文件系统模型**：

| 层级 | 名称 | 内容 | 用途 | Token消耗 |
|------|------|------|------|-----------|
| L0 | Abstract | 一句话描述 | 全局语义搜索，快速定位相关目录 | 极少 |
| L1 | Overview | 结构化摘要 + 子目录索引 | 目录定位和摘要预览 | 较少 |
| L2 | Content | 完整文档原文 | 仅命中后按需加载 | 按需 |

**优势**：保留了文档的层级语义结构。检索时先在L0/L1层定位到相关目录，再读取L2原文，避免传统RAG"大海捞针"式的扁平检索。

### 2.2 层级递归检索算法

```
输入: 用户Query
  1. Query → Embedding向量化
  2. 全局向量检索 TOP-K（检索L0摘要）
  3. 合并起始点，加入优先队列
  4. 递归检索:
     while 队列非空:
       取出当前最高分目录
       检索该目录下的子节点
       if L2节点: 收集为候选结果
       else: 分数传播 → 加入队列继续递归
  5. Rerank精排（可选）
  6. 返回排序后的L2原文
```

**分数传播公式**: `final_score = α × child_score + (1-α) × parent_score`

其中α默认0.5，平衡父目录语义和子节点匹配度。

### 2.3 混合索引

- **Dense Vector** (密集向量): 1024/3072维，捕获深层语义相似度
- **Sparse Vector** (稀疏向量): {term: weight}，保留精确关键词匹配
- **混合检索**: Dense + Sparse 双路召回，兼顾语义泛化和精准匹配

### 2.4 意图路由

在Agent执行前，使用轻量级LLM调用进行意图分类，避免非知识类请求进入完整Agent Loop：

| 意图 | 响应延迟 | 处理方式 |
|------|----------|----------|
| 知识查询 | 正常 | 进入完整Agent Loop |
| 寒暄/问候 | < 1s | 直接返回预设回复 |
| 能力问询 | < 1s | 系统能力介绍 |
| 越狱/越权 | < 1s | 安全拦截 |
| 会话回顾 | < 1s | 返回近期摘要 |

### 2.5 多通道深度适配

各通道不只是做消息文本转发，而是深度适配平台特性：

- **飞书**: WebSocket长连接（无需公网IP），交互式卡片渲染，支持emoji状态反馈
- **钉钉**: Stream模式 + **动态活体卡片**。卡片实时更新AI处理进度："消息卡片生成中..." → "检索知识库" → "文档读取完成" → 最终答案
- **Web页面**: 完整聊天UI + 会话历史侧栏 + PDF导出 + 人工接管按钮
- **REST API**: 标准JSON格式，第三方系统可集成

### 2.6 会话记忆与持续学习

```
会话消息 → commit archive → archive summary
    → MemoryExtractor (提取关键信息)
    → Dedup/Merge (去重合并)
    → 长期记忆存储 → 下次检索可用
```

- **记忆作用域**: 支持 user-scoped（用户级记忆隔离）和 agent-scoped（共享知识提取）
- **触发机制**: 会话结束/用户主动`/remember`命令/超过记忆窗口自动触发

### 2.7 人工接管

- AI判断无法确认答案、识别投诉/敏感意图时，建议转人工
- 用户可主动点击"转人工"按钮
- 接管时传递完整会话上下文 + AI已检索到的相关文档
- 支持配置远程接管服务URL

## 三、难点与解决方案

### 难点1: 传统RAG检索效果差

**问题**: 扁平向量存储丢失文档结构信息，检索结果缺少上下文关联。

**解决**: 设计L0/L1/L2三级层级结构 + 递归目录检索算法。保留文档目录语义，检索时先定位目录再检索内容，结果更精准且有上下文脉络。

### 难点2: 多通道消息格式差异大

**问题**: 飞书、钉钉、Web等通道的消息格式、交互模式各不相同，统一处理困难。

**解决**: 抽象BaseChannel接口，每个通道独立实现消息解析和渲染。钉钉通道创新性地实现了动态活体卡片，在Agent处理过程中实时更新卡片内容，给用户"AI在思考"的体感反馈。

### 难点3: 检索质量不可观测

**问题**: 传统RAG是黑盒，回答质量好与坏无法追溯到检索环节的具体问题。

**解决**: 每次检索返回带URI的溯源结果。管理后台提供"召回测试"页面，可针对单个Query查看完整检索轨迹（命中了哪些目录、L0/L1/L2分别的分数、最终选用了哪些文档），支持检索策略调优。

### 难点4: 知识持续更新与记忆迭代

**问题**: 产品文档更新后知识库需同步；客服对话中的经验知识需要沉淀。

**解决**: 文档更新支持增量索引；会话自动提取长期记忆，经过去重和合并后进入知识库，实现"越用越聪明"的正向循环。

## 四、部署说明

### 4.1 环境要求

| 项目 | 要求 |
|------|------|
| 操作系统 | Linux / macOS |
| Python | 3.10+ |
| 内存 | 最低4GB，推荐8GB |
| 存储 | 根据知识库大小，通常10-50GB |
| 网络 | 需访问LLM API（火山引擎/OpenAI等） |

### 4.2 部署步骤

```bash
# 1. 克隆项目
git clone <repo-url> && cd OpenViking

# 2. 配置
cp ov.conf.example ov.conf
# 编辑 ov.conf: 填写LLM API Key、Embedding配置、通道配置

# 3. 启动
docker compose up -d

# 4. 验证
curl http://localhost:8080/health    # OpenViking
curl http://localhost:8100/bot/v1/health  # VikingBot
```

### 4.3 关键配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `SCORE_PROPAGATION_ALPHA` | 0.5 | 父子分数权重 |
| `MAX_CONVERGENCE_ROUNDS` | 3 | 检索最大递归轮数 |
| `memory_window` | 50 | 会话消息窗口大小 |
| `max_iterations` | 50 | Agent Loop最大迭代次数 |
