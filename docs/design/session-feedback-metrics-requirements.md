# 会话反馈指标需求文档

## 背景

Admin 分析页当前展示了一个由显式消息反馈计算出来的满意度指标：

```text
positive_feedback_count / feedback_count
```

这个计算本身适合作为“显式反馈中的好评占比”，但如果 UI 文案叫“满意率”，容易让人误以为沉默用户也进入了分母。在这个产品里，大多数用户在系统正常工作时很可能不会点击反馈按钮。点击“赞”更像是回答超出预期，点击“倒赞”则是更强的失败信号。

因此，统计模型需要把显式态度、反馈覆盖度、负向风险和赞赏行为拆开表达。

## 目标

- 让 Admin UI 能区分“显式反馈”和“沉默”。
- 将沉默视为未知状态，而不是自动正向或自动负向投票。
- 展示四个公式稳定、语义明确的指标：
  - 显式好评率
  - 反馈覆盖率
  - 倒赞率
  - 赞赏率
- 保留现有已落盘的反馈数据和历史会话。
- 除非后续 API 需求明确要求持久化派生指标，否则后端存储继续以原始计数为准。
- 指标只面向 Admin / 运维分析场景展示，普通用户不可见。

## 非目标

- 本阶段不从沉默中推断用户满意度。
- 不新增 `up` 和 `down` 以外的反馈值。
- 不改变消息反馈的记录和清除方式。
- 暂不基于转人工、重新打开、连续追问等行为构建隐式解决率。
- 不为非 Admin 客户端新增派生指标 API；普通用户没有查看这些运维指标的职责。

## 定义

### 原始计数

现有原始字段继续作为事实源。

| 字段 | 含义 |
| --- | --- |
| `assistant_message_count` | 会话或日期桶内的 assistant 回复数。 |
| `feedback_count` | 有显式反馈的 assistant 回复数。 |
| `positive_feedback_count` | 显式 `up` 反馈数。 |
| `negative_feedback_count` | 显式 `down` 反馈数。 |

### 派生指标

| 指标 | 公式 | 空状态规则 | 产品含义 |
| --- | --- | --- | --- |
| 显式好评率 | `positive_feedback_count / feedback_count` | `feedback_count == 0` 时显示 `-`。 | 在给出反馈的用户中，正向反馈占比。 |
| 反馈覆盖率 | `feedback_count / assistant_message_count` | `assistant_message_count == 0` 时显示 `-`，否则允许显示 `0%`。 | 有多少回答量拿到了显式反馈。 |
| 倒赞率 | `negative_feedback_count / assistant_message_count` | `assistant_message_count == 0` 时显示 `-`，否则允许显示 `0%`。 | 每条 assistant 回复收到明确失败信号的比例。 |
| 赞赏率 | `positive_feedback_count / assistant_message_count` | `assistant_message_count == 0` 时显示 `-`，否则允许显示 `0%`。 | 回答获得显式正向反馈的频率。 |

## 产品解释

- 显式好评率回答的是：“愿意表达态度的用户里，正向占比是多少？”
- 反馈覆盖率回答的是：“显式反馈样本对整体回答量的覆盖程度如何？”
- 倒赞率回答的是：“bot 产出明确糟糕体验的频率有多高？”
- 赞赏率回答的是：“bot 的回答有多常超出预期，值得用户主动点赞？”

沉默回复应被视为“未知 / 未采样”。它们可能是正常完成的使用，但在没有独立隐式成功模型前，系统不应该把它们标记为满意。

## 示例

100 条 assistant 回复，5 个赞，5 个倒赞：

| 指标 | 数值 |
| --- | --- |
| 显式好评率 | `5 / 10 = 50%` |
| 反馈覆盖率 | `10 / 100 = 10%` |
| 倒赞率 | `5 / 100 = 5%` |
| 赞赏率 | `5 / 100 = 5%` |

100 条 assistant 回复，没有任何反馈：

| 指标 | 数值 |
| --- | --- |
| 显式好评率 | `-` |
| 反馈覆盖率 | `0%` |
| 倒赞率 | `0%` |
| 赞赏率 | `0%` |

## 面向用户的文案要求

- 将公式为 `up / feedback` 的指标从含糊的“满意率”改为“显式好评率”。
- `feedback / assistant replies` 使用“反馈覆盖率”。
- `down / assistant replies` 使用“倒赞率”。
- `up / assistant replies` 使用“赞赏率”。
- 说明文字需要暴露分子和分母，例如 `8 / 10 条反馈为赞` 或 `10 / 100 条回复有反馈`。
- 显式好评率无反馈时显示 `-`，辅助文案可使用 `暂无反馈`。

## 实现要求

- Admin 前端从现有 API 字段派生指标。
- 按日分析和会话列表/详情 API 保持向后兼容。
- 本阶段不新增 API 层派生指标字段，尤其不向普通用户端暴露这些指标。
- 复用现有会话跳转和排序行为：
  - 倒赞率钻取继续按 `negative_feedback_count` 排序。
  - 反馈覆盖率钻取继续按 `feedback_count` 排序。
  - 赞赏率钻取继续按 `positive_feedback_count` 排序。
- 状态语义必须有文本表达；颜色可以辅助 warning/success，但不能是唯一信息来源。

## 已确认决策

- Dashboard 顶部 KPI 行保留一个质量卡片“显式好评率”，其余质量信号放在首屏可见的次级质量区。
- 非 Admin 客户端不新增 API 层派生指标；普通用户不可见这些指标。
- 后续会单独设计“隐式转化率 / 隐式完成率”，但它不得替代显式好评率，也不得简单等同于“沉默 = 成功”。
