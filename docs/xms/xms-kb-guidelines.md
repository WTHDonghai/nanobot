# XMS 技术支持客服机器人知识库文档整理说明

## 1. 文档目的

本文档用于规范 XMS 技术支持客服机器人知识库资料的整理方式，确保知识库中的文档适合被系统稳定导入、准确检索、快速定位和直接引用，满足技术支持、操作指导、常见问题解答、故障排查和人工转接前置判断等业务场景。

结合本项目设计，知识库不是普通资料堆放区，而是面向机器人检索的结构化资源树。文档整理必须同时满足以下目标：

- 让机器人能够先找到正确目录，再找到正确文档，再定位到正确章节。
- 让同一知识点只有一个权威来源，避免检索到多份相互重复或不一致的答案。
- 让客服场景中的“怎么做、为什么错、如何排查、何时转人工”都有明确落点。
- 让后续维护、增量更新和版本替换可持续进行。

## 2. 适用范围

适用于纳入 XMS 技术支持客服机器人知识库的全部文档，包括但不限于：

- 系统基础说明
- 登录与认证说明
- 组织、工号、角色、权限配置
- 房价码、房类房号等基础档案配置
- 前台、预订、在住、结账等业务流程
- 餐饮及增值业务操作说明
- 报表、对账、财务相关说明
- 外设、接口、集成相关说明
- 故障排查、异常处理、应急说明
- 发布变更、版本说明、升级注意事项

## 3. 整理原则

### 3.1 单一事实来源

同一个知识点只能有一个主文档作为权威来源。其他文档如果需要引用，只能通过“关联文档、相关说明、参考链接”的方式指向主文档，不得复制一段相同或近似的正文重复出现。

### 3.2 目录唯一归属

每份文档必须有唯一归属目录，不允许同一份业务内容同时放入多个分类目录。若一个主题横跨多个模块，应按照“用户最可能提问时的主入口”归类，并在其他目录放导航说明，不重复放正文。

### 3.3 面向检索而写

本项目采用目录层级检索和分层内容访问机制。文档不仅要给人看，也要让机器人能检索到。因此标题、目录、章节名、关键术语、步骤描述都必须清晰、标准、可识别。

### 3.4 证据优先

XMS 机器人回答问题前必须先拿到知识库依据。文档正文要能直接作为回答证据使用，不能只有模糊目录、截图合集或不成体系的备注。

### 3.5 一文一主题

每个文档聚焦一个明确主题，不把多个弱相关主题混在同一文档内。避免出现“大而全”的综合文档，导致机器人检索到不相关段落。

### 3.6 结构稳定

同类文档尽量采用同一套标题结构和命名规则，减少不同编写人造成的格式漂移。

### 3.7 可维护、可替换

文档应支持后续增量更新。版本变化时，优先更新原有权威文档；确需分版本维护时，要在标题、元信息和目录层级中显式区分。

## 4. 基本要求

知识库文档至少满足以下要求：

1. 统一使用 `docx` 格式，便于标准化沉淀和后续管理。
2. 标题层级清晰、标准，必须正确使用标题样式，不得只靠加粗或放大字号模拟标题。
3. 内容归类精确，不能同一块内容同时有多个表述、出现在多个文档中。
4. 文档归类清晰，能明确归属于唯一模块和唯一业务主题。
5. 文档标题能直接表达主题，不使用“说明一”“操作补充”“新文档”等无意义命名。
6. 同一文档内术语统一，模块名称、按钮名称、菜单路径、状态码写法保持一致。
7. 文档必须标明适用范围，如适用版本、角色、端别、酒店范围、前置条件。
8. 操作类文档必须具备可执行步骤，故障类文档必须具备可判断的现象、原因和处理方式。
9. 图片、表格、附件必须与正文有明确对应关系，不能只贴图不解释。
10. 文档必须可追溯，需保留责任人、更新时间、来源依据或审核状态。
11. FAQ 类资料不得成为唯一权威来源，FAQ 只做问法映射和导航，不承载重复正文。
12. 禁止把聊天记录、零散截图、未整理备忘、未经确认的经验结论直接纳入正式知识库。

## 5. 结合项目设计的特殊要求

### 5.1 适配分层内容访问

系统会基于文档结构生成摘要、概览和正文三级内容。因此：

- 文档标题必须准确，便于生成高质量摘要。
- 一级、二级、三级标题都要能独立表达语义。
- 正文中不要出现大段没有标题的混合内容。
- 章节不宜过大，超长章节应按业务步骤或问题场景继续拆分。

### 5.2 适配目录递归检索

系统会先定位高相关目录，再向下递归检索文档。因此目录层级要体现业务边界，不能把完全不同类型的资料放在同一层混排。

### 5.3 适配证据抽取

机器人最终回答常依赖某一章节正文，而不是整份文档目录。为便于抽取：

- 关键知识点应直接写在对应章节正文中。
- 不要只在目录页列出标题，不写实际内容。
- 章节标题下第一段应尽快给出定义、规则、结论或步骤起点。

### 5.4 适配图文发送

操作指南和 SOP 类文档可以配图，但图片必须紧贴对应步骤，且图片说明与步骤一致，便于机器人后续把相关图片发给用户。

## 6. 推荐知识库分类体系

建议在知识库根目录下，按 XMS 技术支持业务场景统一规划一级分类：

| 一级分类 | 说明 | 典型内容 |
| --- | --- | --- |
| `00-总则与索引` | 全库导航、命名规则、术语表、目录索引 | 知识库总索引、术语表、角色说明 |
| `01-系统基础与环境` | 安装、部署、访问环境、客户端基础 | 运行环境安装、浏览器要求、网络要求 |
| `02-账号组织与权限` | 工号、角色、权限、组织结构、安全策略 | 员工工号管理、角色权限管理、特殊权限设置 |
| `03-登录与安全` | 登录方式、授权认证、密码策略、账号异常 | 授权登录、扫码登录、AD 域登录、密码异常 |
| `04-基础档案配置` | 房价码、房类房号、基础参数、商品档案 | 房价码设置、房类房号管理、客房商品明细 |
| `05-前台与预订业务` | 预订、入住、换房、续住、结账等核心流程 | 宾客状态、预订流程、入住办理、离店结账 |
| `06-餐饮与增值业务` | 餐饮、桌台、菜谱、附加服务等 | 餐饮菜谱管理、餐饮桌号管理 |
| `07-报表财务与对账` | 报表、账务、审计、日结、对账 | 财务报表、账务处理、对账说明 |
| `08-接口外设与集成` | 门锁、身份证阅读器、支付、接口联调 | 外设配置、接口说明、设备故障 |
| `09-故障排查与应急处理` | 以“现象-原因-处理”组织的排障文档 | 登录失败、打印失败、接口超时 |
| `10-版本变更与公告` | 发布说明、升级影响、废弃能力说明 | 版本更新说明、升级注意事项 |
| `11-案例与问答导航` | 仅做问法导航和案例索引，不做重复正文 | FAQ 索引、场景问答入口、案例导航 |

说明：

- `11-案例与问答导航` 只做导航和问法映射，不重复复制操作步骤和规则正文。
- 同一主题若既有“操作方法”又有“故障排查”，应分别进入对应分类，不混成一篇。

## 7. 文档类型与唯一归属规则

为避免重复建设，建议按文档类型明确主归属：

| 文档类型 | 主要回答的问题 | 应放位置 | 是否可以作为权威来源 |
| --- | --- | --- | --- |
| 规则说明类 | 是什么、有什么规则、字段如何定义 | 对应业务模块目录 | 是 |
| 操作 SOP 类 | 如何操作、步骤是什么 | 对应业务模块目录 | 是 |
| 故障排查类 | 为什么失败、如何排查、如何恢复 | `09-故障排查与应急处理` 或对应模块下的故障子目录 | 是 |
| 参数配置类 | 参数含义是什么、如何配置 | 对应业务模块目录 | 是 |
| 发布变更类 | 新版本改了什么、影响什么 | `10-版本变更与公告` | 是 |
| FAQ 导航类 | 用户常怎么问、该看哪份文档 | `11-案例与问答导航` | 否 |
| 培训案例类 | 某次问题如何处理、案例经验是什么 | `11-案例与问答导航` 或案例目录 | 否，除非明确升级为标准文档 |

归属判断规则：

1. 回答“是什么”的内容，归规则说明类。
2. 回答“怎么做”的内容，归操作 SOP 类。
3. 回答“为什么错、怎么修复”的内容，归故障排查类。
4. 回答“这次版本改了什么”的内容，归发布变更类。
5. FAQ 只保留问法、关键词、跳转目标，不重复主文档内容。

## 8. 文档命名规范

### 8.1 一级目录命名

一级目录统一采用“两位数字编号 + 分类名称”格式，例如：

- `01-系统基础与环境`
- `02-账号组织与权限`
- `09-故障排查与应急处理`

### 8.2 文件命名

建议采用以下格式：

`<二级序号>-<模块>-<主题>-<文档类型>.docx`

示例：

- `01-登录认证-授权登录-SOP.docx`
- `02-角色权限-特殊权限设置-规则说明.docx`
- `03-房价码-新增房价码-操作指南.docx`
- `04-授权登录失败-故障排查.docx`

命名要求：

- 文件名中必须体现模块和主题。
- 不使用“最新版”“最终版”“修订版2”“新建文档(1)”等不规范命名。
- 若必须区分版本，放在文档元信息中优先处理；只有长期并行维护多个版本时，才在文件名中增加版本标识。

## 9. 标题层级规范

### 9.1 层级要求

- 标题 1：文档主标题，全文只能有一个。
- 标题 2：一级章节，建议用于“适用范围、前置条件、操作步骤、常见问题、关联文档”等。
- 标题 3：二级章节，建议用于步骤分组、问题分型、原因分类。
- 标题 4：仅在确有必要时使用，不建议超过四级。

### 9.2 禁止事项

- 禁止仅用加粗代替标题样式。
- 禁止标题编号混乱，如 `一、1、(1)` 混用且无规律。
- 禁止出现无语义标题，如“其他”“补充”“说明”。

### 9.3 推荐标题写法

- 使用“模块 + 动作/问题”表达主题。
- 标题应尽量贴近用户问法和业务术语。

示例：

- `3.1 授权登录`
- `3.2 扫码登录`
- `4.1 房价码新增步骤`
- `5.3 登录失败排查`

## 10. 正文编写规范

### 10.1 规则说明类

建议包含以下固定部分：

- 文档名称
- 适用范围
- 业务说明
- 术语/字段定义
- 规则说明
- 注意事项
- 关联文档

### 10.2 操作 SOP 类

建议包含以下固定部分：

- 文档名称
- 适用范围
- 前置条件
- 菜单路径
- 操作步骤
- 结果校验
- 常见异常
- 关联文档

### 10.3 故障排查类

建议包含以下固定部分：

- 问题现象
- 影响范围
- 可能原因
- 排查步骤
- 处理方法
- 恢复验证
- 仍无法解决时的转人工条件
- 关联文档

### 10.4 编写细则

- 一个步骤只描述一个动作，避免一句话包含多个判断和多个操作。
- 菜单路径使用统一格式，例如：`系统管理 > 角色权限 > 特殊权限设置`。
- 状态码、按钮名、字段名、报错信息应原样保留，不要口语化改写。
- 若步骤依赖角色权限、酒店配置或版本开关，必须写清前置条件。
- 若一个问题存在多种处理路径，应按场景分小节，不要混排。

## 11. 去重控制要求

### 11.1 严禁重复正文

以下情况视为重复建设：

- 同一操作步骤在两篇或多篇文档中完整重复。
- 同一状态说明在多个模块文档中分别重写，但内容实质相同。
- FAQ 中复制主文档完整答案。
- 发布公告中重新解释旧规则，而不是引用既有规则文档。

### 11.2 推荐做法

- 建立一份权威主文档，其余文档只做链接式引用。
- FAQ 只保留“问题 -> 查看哪份文档、哪一章节”。
- 同义词、别名、常见问法放入关键词区或索引区，不放重复正文。
- 共性内容尽量沉淀到上层规范文档，再由各模块引用。

## 12. 元信息规范

每份正式知识库文档首页建议包含一张基础信息表，至少包括：

| 字段 | 说明 |
| --- | --- |
| 文档名称 | 标准名称 |
| 所属模块 | 登录、权限、房价码、餐饮等 |
| 文档类型 | 规则说明 / SOP / 故障排查 / 发布说明 |
| 适用版本 | 适用的 XMS 版本或范围 |
| 适用角色 | 前台、管理员、店长、实施、运维等 |
| 适用端别 | PC、Web、移动端、自助机等 |
| 关键字 | 用户常见问法、模块别名、术语 |
| 更新日期 | 最近更新时间 |
| 责任人 | 维护人或维护团队 |
| 审核状态 | 草稿、已审核、已发布、已废弃 |

补充要求：

- 关键字用于提升问法覆盖，但不能替代正文。
- 已废弃文档不得继续作为有效知识来源，应移出正式知识库或标记失效。

## 13. 图片与附件规范

- 仅保留有助于说明步骤、界面位置、报错现象的图片。
- 图片应紧邻对应步骤或对应问题现象。
- 一张图只服务一个核心说明点，避免整屏堆图。
- 图片中涉及账号、手机号、订单号、身份证号等敏感信息必须脱敏。
- 对于复杂操作，优先使用“步骤文字 + 对应截图”的组合。
- 附件若为表单、模板、参数清单，应有明确命名，并在正文说明用途。

## 14. 文档拆分建议

以下情况建议拆成多篇文档：

- 同一文档同时覆盖多个模块。
- 同一文档同时写规则、操作、排障、升级说明，导致结构臃肿。
- 单个章节过长，明显包含多个可独立提问的场景。
- 不同角色、不同版本、不同端别的步骤差异较大。

建议拆分策略：

- 按业务主题拆分，如“授权登录”“扫码登录”“AD 域登录”分别成文。
- 按内容类型拆分，如“房价码规则说明”和“房价码新增 SOP”分开。
- 按问题现象拆分，如“登录失败”“打印失败”“接口超时”分别成文。

## 16. 验收清单

文档入库前，至少完成以下检查：

| 检查项 | 验收标准 |
| --- | --- |
| 格式检查 | 文件为 `docx`，能正常打开，无损坏 |
| 标题检查 | 标题层级正确，样式统一，目录可识别 |
| 归类检查 | 已归入唯一目录，无多处重复存放 |
| 去重检查 | 无重复正文，无冲突表述 |
| 主题检查 | 一文一主题，主题表达明确 |
| 元信息检查 | 版本、角色、维护人、更新时间齐全 |
| 术语检查 | XMS 术语、菜单名、字段名统一 |
| 步骤检查 | 可执行、可复核、可验证 |
| 图片检查 | 图文对应，已脱敏，有说明 |
| 检索检查 | 标题、章节、关键词可支持用户常见问法 |
| 证据检查 | 正文可直接作为机器人回答依据 |
| 发布检查 | 已确认是否为正式有效版本 |

## 17. 建议的整理流程

建议按以下流程推进知识库整理：

1. 先盘点现有文档，形成清单。
2. 按“模块 + 文档类型 + 是否权威”做初步归类。
3. 标记重复文档、过期文档、无归属文档。
4. 先确定一级目录和命名规则，再开始迁移和重写。
5. 为每个知识点确定唯一主文档。
6. 对 SOP、规则、排障、FAQ 分类型重构。
7. 补齐元信息、标题层级、关键词和关联文档。
8. 抽样验证：用真实客服问法测试是否能定位到正确文档和正确章节。
9. 验证通过后再批量入库。

## 18. 最终要求总结

XMS 技术支持客服机器人知识库文档整理的核心，不是“把资料收集起来”，而是“把知识整理成可检索、可引用、可维护、可追责的标准化资源”。最终交付应达到以下状态：

- 用户问一个问题，机器人能找到唯一、明确、可引用的答案来源。
- 相同知识点不会在多个文档中以不同说法重复出现。
- 目录结构能够反映 XMS 业务边界和客服处理路径。
- 规则、操作、排障、FAQ 各司其职，不相互混淆。
- 后续版本更新时，能在原有结构上持续维护，而不是越积越乱。

如需继续推进，下一步可直接基于本说明补一份《XMS 知识库目录模板》和《标准文档模板（SOP/规则/排障）》。
